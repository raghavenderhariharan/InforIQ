From ERP change to governed action

What Infor IQ is, how the whiteboard design turns a data change into a governed action, and which Infor OS components it relies on.

Data leaves the CloudSuites (CSD first), lands in the Data Lake and is loaded into the Data Warehouse, today's canonical source. Changes become events. An agent picks up each event and asks Infor IQ whether it may act. IQ checks the rules and records a decision. Then the agent acts, or a person decides.

What is Infor IQ?

Infor IQ is a layer that teaches AI what Infor's business data means, and checks what an AI agent is allowed to do. It holds no business data itself.

It knows the meaningA defined map of business ideas: purchase order, vendor, “at risk”, and how they connect.
It answers preciselyIt turns a question into exact queries, runs them as the person asking, and says where each answer came from.
It governs actionsBefore an agent approves a PO, IQ checks the rules and records a decision. The agent does the action itself.
Nota databaseNotan AI modelNotan ERP replacementNotwhat runs the actions

An analogy

Picture an office building. The directory says what every room is and how the rooms connect. The security desk checks your badge before you go in. Neither does the work inside the rooms.

IQ is the directory and the security desk for Infor's data and for AI agents. The data stays in the rooms (Data Fabric). The agents still do the work.

Who uses it

AI agents and assistants ask it questions. Stewards curate each customer's own terms. CloudSuite teams supply their product models.

The same question, with and without IQ

“Which open POs are at risk of late delivery?”
Without IQ
  • The agent guesses which tables and columns hold POs and vendors.
  • “At risk” means whatever the model assumes this time.
  • Two runs can give two different answers.
  • There is no record of how the answer was reached.
  • Security depends on each tool the agent happens to use.
With IQ
  • “Open PO” and “at risk” are defined terms and a defined rule.
  • The query is built from that definition, not guessed.
  • It runs as the person asking, so their data security applies.
  • The same data gives the same answer.
  • The result carries provenance: where each piece came from.

The contrast follows the IQ concept page's own “without grounding” and “with grounding” framing.

Walkthrough

One sales order on credit hold, start to finish

Follows the wiki's Credit Hold Release POC on CSD (August 2026). The step numbers match the diagram. Customer, order numbers and amounts are illustrative.

  1. CSD → Data Lake → Data Warehouse

    An order goes on credit hold in CSD

    SO 50112 for $8,000 is placed on hold. The change lands in the Data Lake and is loaded into the CSD warehouse, today's canonical source.

  2. Data Warehouse

    The canonical SalesOrder updates

    IQ will read this copy through Compass, never the live ERP. Iceberg-based Data Lake+ would slot in here later as a configuration change.

  3. Canonical commit → Event Service

    The Data Fabric Event Service publishes the hold

    The event carries the tenant, product CSD, domain Sales, the SalesOrder identity and the action mapping releaseHold. It should go out only after the commit; IDF has not confirmed that yet.

  4. Event Service → agent

    An agent picks it up and opens a case

    The agent does not judge the credit position itself.

  5. Agent → ERX ↔ rules → ledger

    The agent asks IQ: can I release this hold?

    IQ reads the customer's exposure through Compass as the caller and checks the action's precondition: creditExposure + totalOrderAmount ≤ creditLimit. It records the decision first. Under ADR-002 (proposed) that is a write-once S3 record, and if the write fails IQ denies.

  6. Agent → ERP MCP, or ERX → HITL

    The order takes one of three outcomes

    AUTHORIZED: the agent releases the hold through ERP MCP tools. DENIED: the hold stays. REQUIRES_ESCALATION: a person with delegated credit authority decides.

SO 50112 · within the limit

$32,000 exposure + $8,000 = $40,000 ≤ $50,000

AUTHORIZED

The agent releases the hold through ERP MCP tools. The ERP can still refuse.

SO 50140 · over the limit

$32,000 exposure + $26,000 = $58,000 > $50,000

REQUIRES_ESCALATION

A Credit Manager reviews it. Approval runs the release; rejection ends the process and the hold stays.

The POC itself returns only Permit or Deny. The escalation path comes from the Autonomous Use Cases page and the Business Processes proposal (HUMAN_TASK).

Still open

Open questions

Points the wiki pages leave unsettled today.

  • ERX The name used for IQ's reasoning and authorisation core. The wiki does not define it; the likely meaning is "Enterprise Reasoning & eXecution".
  • Events Today the event goes to the agent, which then asks IQ. Should IQ ever subscribe to events directly?
  • Sources CSD comes first. When do SyteLine (CSI), Factory Track and CPQ follow?
  • Data Lake+ Iceberg or Delta, and when it becomes a canonical source alongside the warehouse.
  • Event timing IDF still has to confirm that events go out only after the data is committed.
  • HITL Which rules escalate to a person, and where reviewers do their review.

1 · A grounded question

Current design, part concept
“Which of my open POs are at risk of late delivery?”
  • 1Look up “open” and “at risk” in the ontology
  • 2Ontology becomes SQL
  • 3Compass runs it as the caller
  • 4Rule scores each PO
POVendorAmountRiskEvidence
4521Acme$45,000HIGHVendor averaging 8 days late over the last 5 deliveries
4533Beta$12,000HIGH2 of 4 lines on backorder
4540Gamma$78,000HIGHDue in 3 days and the vendor is 35% late this quarter
4502Delta$20,000OKNo rule fired

Rule: HIGH if the vendor's average delivery time exceeds the days until due, or its late rate is above 20%, or lines are on backorder. Results carry provenance. Same data, same answer, nothing stored.

Basis: the v4.0 worked example, run over the current canonical-data path. Provenance on results is in the current design. Per-field lineage to source columns and a certified glossary are v4.0 concept, and the current design pages do not mention them. Names, amounts and thresholds are the page's illustrative values.

2 · A governed action

Current design, advisory
“Approve this purchase order.” (PO pending approval)

Rules: AI agent up to $10,000 and vendor risk below 3. Purchasing manager up to $50,000. VP procurement has no limit. If the PO is already approved, everyone is denied.

What happens next: on AUTHORIZED, IQ records the decision first, then the agent approves the PO itself through ERP MCP tools. IQ changes nothing, and the ERP can still refuse. On DENIED, nothing happens in the ERP and the reply names the role that could approve.

Advisory today. The current spec returns the decision without a signed token (deferred to IIQ-196), and the decision ledger is being re-scoped as a write-once S3 record (ADR-002, proposed). IQ's authorisation is a policy gate, not proof the ERP can check.

Basis: the v4.0 action definition and denial example, plus the current rule that IQ only authorises. The current design lists three outcomes (AUTHORIZED, DENIED, REQUIRES_ESCALATION). The pages reviewed do not say when escalation applies, so a refusal follows the v4.0 behaviour.

3 · Same question, two tenants

Part concept
“Is this PO a high-value PO?”
Base product (any tenant)orderNumber, totalAmount, isOpen, belongsToVendor. Fields user1 to user9 exist but carry no meaning.
Acme's overlay adds (current)projectCode (user1) and estimatedWeight (user6), by rebinding to existing columns, plus net-new elements such as a ProjectApproval table and an AcmeHighRiskVendor class.

Three layers: shared Core, product base, tenant overlay. The overlay changes things for that tenant only. The base is never edited. The $100,000 threshold column is concept: the current rules let a tenant rebind fields and add new elements, and stewards curate labels, hierarchy, exposed properties and business definitions. Redefining a rule is not on that list.

Basis: the v4.0 layering example, checked against the Revised Architecture (decision D-IDF-11). Field rebinding and additions are current. The threshold override is v4.0 concept only. Removed or renamed base references, and redefining a base column's type, are hard conflicts.

4 · Across two products

Draft, future
“Show this employee's HR events and their gross pay.”
  • 1Find the golden ID in the cross-reference
  • 2Query HR as the caller
  • 3Query Payroll as the caller
  • 4Join in memory
golden id 88213
  HR       person 1042     → 3 employment events
  Payroll  employee PR-771 → gross pay per statement

Security composes by construction. If the agent cannot see Payroll, that query returns nothing and those rows drop out of the join. No “same person” fact is stored. It exists only for the life of the query. The IRI each side mints must match exactly, or the join finds nothing.

Basis: the cross-product layering blueprint (draft, future work). The first delivery is a single product on the CSD warehouse, so this is not in its scope.

5 · The AI Studio connection

Proposal, not in the wiki
AI Studio requirement: “Automatically approve low-risk purchase orders up to the agent limit, and send the rest for review.”
  • 1Architect takes the requirement
  • 2Advisor ranks: keep rules outside the flow
  • 3RPA Analyst resolves terms against IQ's ontology
  • 4You confirm the plan
  • 5RPA Developer builds a flow that asks IQ first
  • 6Bot calls IQ, then approves or files an exception

Highlighted cells change when the limit moves from $10,000 to $25,000. Rule: amount up to the limit and vendor risk score below 3.

Rules in IQ policy: change the limitEdit the policy and the bot is untouched. Where tenant action policies are authored is not defined in the pages reviewed, and decisions go to the decision ledger (ADR-002, proposed).
Rules inside the RPA flow: change the limitAsk AI Studio for an update. The Analyst needs the complete flow restated, the Developer republishes it, and you confirm again.

Needed before this works

  • IQ reachable from AI Studio's agents through the IDF gateway. The pages show no such design.
  • The bot registered as an agent identity in IQ's policy.
  • The tenant's PO and vendor data in IDF canonical datasets (CSD warehouse first).
  • AI Studio's owners agreeing that Analysts may call a reference service.
  • Accepting that IQ checks canonical data while the ERP stays the final arbiter.

Not yet in the IQ design

  • A signed decision token. Without it, a bot that skips IQ is not stopped (deferred to IIQ-196).
  • A finished decision ledger. ADR-002 (proposed) makes it a write-once S3 record under the Govern epic (IIQ-195).
  • A defined place to author tenant action policies, such as the agent limit.
Basis: a proposal, not taken from the wiki. No page reviewed designs this connection. It is assembled from AI Studio's onboarding rules, IQ's /action/authorize contract, and the template workbook's lockbox lesson that validation belongs outside the RPA flow. The limits and PO list are invented, and the "needed" list is unvalidated.

What it will not do

Run actions in the ERP. The agent does that.
Call application APIs for Infor data. It reads canonical data.
Reason probabilistically or predict. Infor's AI platforms do.
Hold an LLM in its deterministic core.
Copy ERP data into a separate store.

Plain words

Eleven terms you will meet

Skim these once and the rest of the page reads easily.

OntologyA defined map of business concepts and how they relate. A PO belongs to a vendor. A PO has lines.
Infor Data Fabric (IDF)Infor's data platform. IQ is now a component inside it.
Canonical datasetInfor's standardised copy of ERP data, held in Data Fabric. IQ reads this, not the live ERP.
CompassThe SQL service IQ uses to read canonical data. It applies the asking user's security.
SPARQLA query language for linked concepts. IQ turns its patterns into SQL for Compass.
Virtual knowledge graphThe linked view of the data, built on demand from SQL and never stored.
Tenant overlayOne customer's own field names and terms, layered over the shared product model.
Reasoning enginesRules, constraint checks and class logic that classify things and explain why. No AI guessing.
GroundingTying an AI answer to defined terms and real records, so it cannot invent what words mean.
MCPA standard way for AI agents to call tools. ERP MCP tools are how an agent actually performs an action.
ADR and Kiro specThe design decision record, and the written specification the team approved. They are the main sources for “current design”.
